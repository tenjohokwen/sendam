       ```java
       @Query("SELECT s.id FROM SendRequest s WHERE s.finalizedAt < :cutoff " +
              "AND s.sendStatus IN (com.softropic.sendam.client.contract.SendRequestStatus.FINALIZED, " +
              "com.softropic.sendam.client.contract.SendRequestStatus.FAIL_FINALIZED)")
       List<Long> findFinalizedBefore(@Param("cutoff") Instant cutoff);

       @Query("DELETE FROM SendRequest s WHERE s.id IN :ids")
       ```

       ```java
       @Modifying
       ```

    3. Create `SmsPurgeService` in `client.service`. Annotate `@Service @RequiredArgsConstructor @Slf4j`. Dependencies: `SendRequestRepository`, `SendRequestRecipientRepository`.

       Method `purgeOldMessages()` annotated `@Scheduled(cron = "0 0 2 * * *")` (daily at 2am) and `@Transactional`:
       - Compute cutoff: `Instant.now().minus(30, ChronoUnit.DAYS)`.
       - Find IDs to purge: `List<Long> ids = sendRequestRepository.findFinalizedBefore(cutoff)`.
       - If ids is empty: log DEBUG "No messages to purge" and return.
       - Process in batches of 500 to avoid unbounded delete statements: partition ids into sublists of 500.
       - For each batch:
         a. `recipientRepository.deleteBySendRequestIdFkIn(batch)` — delete children first (FK constraint)
         b. `sendRequestRepository.deleteAllByIdIn(batch)` — delete parents after children
       - Log INFO "Purged {} send_request records (finalized_at < {})", ids.size(), cutoff.

       Batching reason: PostgreSQL can handle large IN clauses but it is good practice to avoid 10,000-element IN lists. 500 is safe for the parameter count.

       Do NOT add `@EnableScheduling` — it is already on `ClientConfig`. The cron job will be picked up automatically by the existing scheduler infrastructure.
  </action>
