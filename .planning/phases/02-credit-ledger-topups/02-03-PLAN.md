<objective>
Implement the atomic credit reservation service that Phase 3 SMS send will call. CreditReservationService is the financial enforcement layer: it holds the SELECT FOR UPDATE lock, checks balance, writes ledger entries, and guarantees no two concurrent sends can together drive balance negative. This plan builds the service and its unit tests only — no new HTTP endpoints are added. Phase 3 wires it to POST /v1/sms/send.

Purpose: Satisfies CREDIT-03 (balance never goes negative, reservation is atomic). This is the hardest correctness requirement in the system. The tests written here serve as the permanent regression suite for that invariant.
Output: CreditReservationService with reserve/release/debit, and a unit test class that proves the concurrent reservation invariant using mocks.
</objective>

Create CreditReservationService.java in com.softropic.sendam.client.service:
- @Service, @Transactional at class level, @Slf4j, @RequiredArgsConstructor
- Inject: ClientCreditBalanceRepository balanceRepository, CreditLedgerRepository ledgerRepository

Method: long reserve(Long clientId, long amount, String reference)
- amount must be > 0; throw IllegalArgumentException("reserve amount must be positive") if not
- Acquire lock: ClientCreditBalance lockRow = balanceRepository.findByClientIdForUpdate(clientId)
    .orElseThrow(() -> new ResourceNotFoundException("No credit balance row for client: " + clientId))
- long currentBalance = lockRow.getBalance();
- if (currentBalance < amount): throw InsufficientBalanceException("Insufficient balance: available=" + currentBalance + ", requested=" + amount)
- long newBalance = currentBalance - amount;
- Write SMS_RESERVATION entry:
    CreditLedgerEntry entry = CreditLedgerEntry.builder()
        .clientId(clientId)
        .entryType(LedgerEntryType.SMS_RESERVATION)
        .amount(-amount)           // negative: debit
        .balanceAfter(newBalance)
        .reference(reference)
        .status(EntityStatus.ACTIVE)
        .build();
    CreditLedgerEntry saved = ledgerRepository.save(entry);
- Update lock row: lockRow.setBalance(newBalance); balanceRepository.save(lockRow);
- return saved.getId();   // this is the reservationId — Phase 3 passes it back to debit/release

Method: void release(Long clientId, Long reservationId)
- Load original reservation entry: CreditLedgerEntry reservation = ledgerRepository.findById(reservationId)
    .orElseThrow(() -> new ResourceNotFoundException("Reservation entry not found: " + reservationId))
- Verify the entry belongs to this client and is an SMS_RESERVATION:
    if (!reservation.getClientId().equals(clientId)) throw new ResourceNotFoundException("Reservation not found for client")
    if (reservation.getEntryType() != LedgerEntryType.SMS_RESERVATION) throw new IllegalStateException("Entry " + reservationId + " is not a reservation")
- long releasedAmount = Math.abs(reservation.getAmount());   // reservation.amount is negative, negate it
- Acquire lock: ClientCreditBalance lockRow = balanceRepository.findByClientIdForUpdate(clientId)
    .orElseThrow(() -> new ResourceNotFoundException("No credit balance row for client: " + clientId))
- long newBalance = lockRow.getBalance() + releasedAmount;
- Write SMS_REFUND entry:
    ledgerRepository.save(CreditLedgerEntry.builder()
        .clientId(clientId)
        .entryType(LedgerEntryType.SMS_REFUND)
        .amount(releasedAmount)    // positive: credit
        .balanceAfter(newBalance)
        .reference("release:" + reservationId)
        .status(EntityStatus.ACTIVE)
        .build());
- lockRow.setBalance(newBalance); balanceRepository.save(lockRow);

Method: void debit(Long clientId, Long reservationId, long actualAmount)
- actualAmount must be > 0; throw IllegalArgumentException if not
- Load original reservation entry (same as release — verify client ownership and SMS_RESERVATION type)
- long reservedAmount = Math.abs(reservation.getAmount());
- if (actualAmount > reservedAmount): throw IllegalArgumentException("actualAmount " + actualAmount + " exceeds reserved amount " + reservedAmount)
- Acquire lock: ClientCreditBalance lockRow = balanceRepository.findByClientIdForUpdate(clientId) ...
- long currentBalance = lockRow.getBalance();
  NOTE: balance was already reduced by reserve(); do NOT subtract actualAmount again from the lock row.
  The lock row already reflects the reservation deduction. What we need to do here is:
  - If actualAmount == reservedAmount: no balance change needed; write SMS_DEBIT entry with amount=-actualAmount, balanceAfter=currentBalance (balance is correct)
  - If actualAmount < reservedAmount: write SMS_DEBIT for -actualAmount AND SMS_REFUND for +(reservedAmount - actualAmount); new balance = currentBalance + (reservedAmount - actualAmount)
- long overReservation = reservedAmount - actualAmount;
- Write SMS_DEBIT entry:
    ledgerRepository.save(CreditLedgerEntry.builder()
        .clientId(clientId)
        .entryType(LedgerEntryType.SMS_DEBIT)
        .amount(-actualAmount)
        .balanceAfter(currentBalance + overReservation)   // = currentBalance if overReservation==0
        .reference("debit:" + reservationId)
        .status(EntityStatus.ACTIVE)
        .build());
- If overReservation > 0, write SMS_REFUND entry:
    ledgerRepository.save(CreditLedgerEntry.builder()
        .clientId(clientId)
        .entryType(LedgerEntryType.SMS_REFUND)
        .amount(overReservation)
        .balanceAfter(currentBalance + overReservation)
        .reference("over-reservation:" + reservationId)
        .status(EntityStatus.ACTIVE)
        .build());
    lockRow.setBalance(currentBalance + overReservation);
    balanceRepository.save(lockRow);
- If overReservation == 0: no change to lockRow balance (already correct from reserve())

IMPORTANT correctness notes for the implementer:
- Every method must be @Transactional (class-level annotation covers all methods)
- findByClientIdForUpdate MUST be called in every balance-mutating method — this is the serialization point
- Do NOT call CreditService.applyLedgerEntry() here — CreditReservationService manages its own lock acquisition to avoid nested lock acquisition on the same row within one transaction (which is fine in PostgreSQL but creates an implicit dependency on call ordering that is fragile). Keep CreditReservationService self-contained.
- The SELECT FOR UPDATE will block concurrent transactions for the same clientId. This is intentional. The 2000ms lock.timeout QueryHint on findByClientIdForUpdate means a stuck transaction will unblock callers within 2 seconds (they receive a LockTimeoutException that propagates as 503 — add handler to ApiAdvice in Phase 3 when the endpoint exists).

      // simulate the lock row mutation as it would happen in a real DB transaction:
      // we will update sharedBalance when save is called
      return Optional.of(row);
  });

      sharedBalance.set(saved.getBalance());

  });

      // give it a fake id
      return e;
