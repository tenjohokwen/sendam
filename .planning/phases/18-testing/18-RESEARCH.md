# Phase 18: Testing - Research

**Researched:** 2026-03-14
**Domain:** Vitest + Vue Test Utils for Quasar 2 / Vue 3 Composition API components
**Confidence:** HIGH (stack, patterns verified via official sources); MEDIUM (Quasar-specific $q.notify workarounds from community issues)

---

## Summary

Phase 18 must add Vitest + Vue Test Utils coverage for every component introduced in v1.2 (Phases 13–17). No test infrastructure exists today: no `vitest.config.js`, no test files, no testing libraries in `package.json`. Everything must be installed and configured from scratch.

The official path for Quasar + Vitest is the `@quasar/quasar-app-extension-testing-unit-vitest` extension, which installs the testing harness via `quasar ext add @quasar/testing-unit-vitest`. This extension produces a `vitest.config.js` (or `.mjs`) and an `installQuasarPlugin` helper consumed in each test file. Because the project already uses `"type": "module"` in `package.json`, the config file must use the `.mjs` extension.

The critical discovery is that `$q.notify` (accessed via `useQuasar()`) is tricky to spy on in the jsdom environment. The cleanest approach per community resolution is to spy on it **after** mount: `wrapper.vm.$q.notify = vi.fn()` — then assert on it. For components that call `$q.notify` in the same tick as a function call, wrapping the call in `await nextTick()` + `flushPromises()` is required before the assertion.

**Primary recommendation:** Install via `quasar ext add @quasar/testing-unit-vitest`, pass a real i18n instance as a plugin (not a `$t` mock) so translation keys are verifiable, mock the `adminApi` module with `vi.mock`, and patch `$q.notify` post-mount.

## Standard Stack

### Core
| Library | Version | Purpose | Why Standard |
|---------|---------|---------|--------------|
| vitest | ^2.x (installed by extension) | Test runner | Vite-native, fast, compatible with `@quasar/app-vite` v2 |
| @vue/test-utils | ^2.x (installed by extension) | Vue component mount/assert | Official Vue testing utility |
| @quasar/quasar-app-extension-testing-unit-vitest | latest | Quasar-specific test harness | Provides `installQuasarPlugin`, `vitest.config.mjs`, JSX transform |
| @vitest/ui | optional | Browser UI for test runs | Developer convenience only |
| jsdom | installed by extension | DOM environment | Standard for component unit tests without a real browser |

### Supporting
| Library | Version | Purpose | When to Use |
|---------|---------|---------|-------------|
| @pinia/testing | ^0.1.x | `createTestingPinia()` | Components that read `useUserStore` |
| happy-dom | alternative to jsdom | Faster DOM | Can swap if jsdom proves slow — not required |

### Alternatives Considered
| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| jsdom | happy-dom | happy-dom is faster but less feature-complete; jsdom is the Quasar extension default |
| `installQuasarPlugin` | manually passing `Quasar` plugin | Manual approach works but loses auto-restore after each suite |
| real i18n instance | `$t: (k) => k` mock | `$t` mock is simpler but hides missing key bugs; real instance is preferred |

### Installation

```bash
# From inside src/frontend/
quasar ext add @quasar/testing-unit-vitest
```

The extension will:
- Add `vitest`, `@vue/test-utils`, and related packages to `devDependencies`
- Create `vitest.config.mjs` (ESM extension required because `package.json` has `"type": "module"`)
- Create `test/vitest/setup-file.ts` (or `.js`)
- Add `"test": "vitest"` script to `package.json`

After install, add to `package.json` scripts:
```json
"test": "vitest",
"test:ui": "vitest --ui"
```

### Pattern 1: Standard Component Test File Structure

Every test file follows this shell:

```javascript
// Source: https://testing.quasar.dev/packages/unit-vitest/
import { installQuasarPlugin } from '@quasar/quasar-app-extension-testing-unit-vitest'
import { mount, flushPromises } from '@vue/test-utils'
import { createI18n } from 'vue-i18n'
import { vi, describe, it, expect, beforeEach } from 'vitest'
import messages from 'src/i18n'           // real translation messages
import { adminApi } from 'src/api/admin'  // will be vi.mock'd
import MyComponent from 'src/pages/admin/MyComponent.vue'

vi.mock('src/api/admin')                  // auto-mock entire module

installQuasarPlugin({ plugins: { Notify } })  // Notify needed for $q.notify

const i18n = createI18n({ locale: 'en-US', legacy: false, messages })

function mountComponent(props = {}) {
  const wrapper = mount(MyComponent, {
    global: {
      plugins: [i18n],
    },
    props,
  })
  // Patch $q.notify post-mount (workaround for quasar-testing#221)
  wrapper.vm.$q.notify = vi.fn()
  return wrapper
}

describe('MyComponent', () => {
  beforeEach(() => {
    vi.clearAllMocks()
  })

  it('loads data on mount', async () => {
    adminApi.getSomething.mockResolvedValue([...])
    const wrapper = mountComponent()
    await flushPromises()
    // assertions
  })
})
```

### Pattern 2: vitest.config.mjs

The extension generates this; the key parts to confirm are:

```javascript
// vitest.config.mjs
import { defineConfig } from 'vitest/config'
import vue from '@vitejs/plugin-vue'
import { quasar, transformAssetUrls } from '@quasar/vite-plugin'
import { fileURLToPath } from 'node:url'
import { resolve } from 'node:path'

export default defineConfig({
  test: {
    environment: 'jsdom',
    setupFiles: ['test/vitest/setup-file.js'],
    globals: true,       // allows describe/it/expect without imports
  },
  plugins: [
    vue({ template: { transformAssetUrls } }),
    quasar({ sassVariables: false }),  // no sass in tests
  ],
  resolve: {
    alias: {
      src: fileURLToPath(new URL('./src', import.meta.url)),
      // '#q-app/wrappers' must be aliased or boot files will fail to import
    },
  },
})
```

**Critical alias issue:** Components import from `src/boot/axios` which imports `#q-app/wrappers`. This symbol is only available inside the Quasar build pipeline. In Vitest's jsdom environment it does not exist. The solution: mock `src/boot/axios` entirely in tests (or in `setup-file.js`), so the boot file is never executed during tests.

### Pattern 3: Mocking the api/ Layer

All API calls go through `src/api/admin/index.js` (the `adminApi` object). Mock the entire module:

```javascript
// In test file, before any imports resolve at runtime:
vi.mock('src/api/admin', () => ({
  adminApi: {
    getClients:             vi.fn(),
    createClient:           vi.fn(),
    getApiKeys:             vi.fn(),
    createApiKey:           vi.fn(),
    revokeApiKey:           vi.fn(),
    getTopupHistory:        vi.fn(),
    approveTopup:           vi.fn(),
    rejectTopup:            vi.fn(),
    getScheduledSms:        vi.fn(),
    getDlrForRequest:       vi.fn(),
    getWebhookEndpoints:    vi.fn(),
    getWebhookDeliveries:   vi.fn(),
    getDeliveryStats:       vi.fn(),
    getCreditSummary:       vi.fn(),
    getCircuitBreakerHealth: vi.fn(),
    getProviderStats:       vi.fn(),
    getWebhookHealth:       vi.fn(),
  }
}))
```

Then in each test: `adminApi.getClients.mockResolvedValue([...])` for success, `adminApi.getClients.mockRejectedValue(networkError)` for failure.

### Pattern 4: Testing $q.notify

`useQuasar()` is used in TopupsPage, ApiKeysDialog, CreateClientDialog, and RawKeyDialog to call `$q.notify`. Because jsdom's Notify plugin does not call real DOM, the call succeeds silently — but to assert it was called:

```javascript
// After mount(), patch notify on the instance
wrapper.vm.$q.notify = vi.fn()

// Trigger the action
await wrapper.find('[data-test="approve-btn"]').trigger('click')
await flushPromises()

expect(wrapper.vm.$q.notify).toHaveBeenCalledWith(
  expect.objectContaining({ type: 'positive' })
)
```

Alternative: pass `Notify` plugin to `installQuasarPlugin` and spy on `Notify.create`. But the post-mount patch is simpler and reliably works per community issue resolution.

### Pattern 5: Testing i18n

Use a real `createI18n` instance with the actual messages object so tests validate that the correct translation keys exist:

```javascript
import { createI18n } from 'vue-i18n'
import messages from 'src/i18n'

const i18n = createI18n({
  locale: 'en-US',
  legacy: false,      // must match boot/i18n.js
  messages,
})

// Pass as plugin in mount:
mount(Component, { global: { plugins: [i18n] } })
```

Do NOT use `$t: (k) => k` mock for this project. The project has 32+ keys per page; a broken key reference would pass silently with a `$t` mock. Using the real instance reveals missing keys immediately.

### Pattern 6: ServerPagination Interaction

ServerPagination emits `page-change` with a 0-based index (internal conversion from 1-based QPagination). To test a parent component reacting to pagination:

```javascript
// Find the ServerPagination child component
const pagination = wrapper.findComponent(ServerPagination)

// Simulate page change (mimics QPagination emitting update:model-value)
await pagination.vm.$emit('page-change', 1)  // page index 1 (0-based)
await flushPromises()

// Assert API was called with correct page
expect(adminApi.getScheduledSms).toHaveBeenCalledWith({ page: 1, size: 20 })
```

For testing ServerPagination itself in isolation, set `totalPages > 1` prop and assert QPagination renders.

### Pattern 7: Dialog Open/Close

Dialogs in this project use two patterns:

**Pattern A** — `v-model` dialog (CreateClientDialog, ApiKeysDialog, RawKeyDialog):
```javascript
// Open: pass modelValue: true as prop
const wrapper = mount(CreateClientDialog, {
  global: { plugins: [i18n] },
  props: { modelValue: true },
})
// Close: assert emit
await wrapper.find('[data-test="cancel-btn"]').trigger('click')
expect(wrapper.emitted('update:modelValue')).toEqual([[false]])
```

**Pattern B** — `v-if` outer guard in parent (ClientsPage's `v-if="showApiKeysDialog && selectedClient"`):
Test the parent page: trigger the "Manage Keys" button, assert `ApiKeysDialog` is rendered. Then trigger close event, assert it disappears.

**Pattern C** — DlrDialog uses `v-model:show` (custom prop name `show`):
```javascript
mount(DlrDialog, {
  props: { show: true, sendRequestId: 'abc123' },
  global: { plugins: [i18n] },
})
```

### Anti-Patterns to Avoid

- **Importing boot files in tests:** `src/boot/axios` uses `#q-app/wrappers` which is Quasar-CLI-only. Never import it in tests. Mock `src/boot/axios` instead.
- **`$t: (k) => k` mock:** Hides missing i18n key bugs. Use the real instance.
- **`v-show` vs `v-if` confusion in assertions:** Dialogs use `v-if`, so a closed dialog has no DOM; `wrapper.find('.q-dialog')` returns empty when `modelValue=false`. Do not assert text content of an unmounted dialog.
- **Not calling `flushPromises()` after async actions:** All API calls are async. `await flushPromises()` is required after triggering any button that calls an API method, before asserting the result.
- **Testing with `shallowMount` for pages that depend on child behavior:** Use `mount` (not `shallowMount`) for page-level tests — child components like ServerPagination need to work. Use `shallowMount` only for pure display card components (DashboardSmsCard, DashboardBillingCard, DashboardSystemCard).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Quasar plugin in jsdom | Custom Quasar setup | `installQuasarPlugin()` | Handles QPagination, QBtn, QBanner, etc. automatically |
| Async promise flushing | `setTimeout(fn, 0)` | `flushPromises()` from `@vue/test-utils` | Correctly drains all microtask queues |
| i18n mock with translate-to-key | `$t: (k) => k` | Real `createI18n` instance | Catches missing key bugs |
| Per-test API mock reset | Manual mock state | `vi.clearAllMocks()` in `beforeEach` | Ensures test isolation |
| Boot file simulation | Importing boot files | Mocking `src/boot/axios` | Boot files use Quasar-CLI symbols unavailable in Vitest |

## Common Pitfalls

### Pitfall 1: `#q-app/wrappers` Not Resolvable in Vitest

**What goes wrong:** Importing any file that transitively imports `src/boot/axios` or `src/boot/i18n` causes `Cannot find module '#q-app/wrappers'` at test startup.

**Why it happens:** `#q-app/wrappers` is a Quasar CLI virtual module only available during Quasar's build/dev pipeline. Vitest doesn't know about it.

**How to avoid:** In `vitest.config.mjs`, add an alias for `#q-app/wrappers` that points to a stub file, OR mock `src/boot/axios` globally in `setup-file.js`:

```javascript
// setup-file.js
vi.mock('src/boot/axios', () => ({
  api: {
    get:    vi.fn(),
    post:   vi.fn(),
    put:    vi.fn(),
    delete: vi.fn(),
  },
  onLoadingChange: vi.fn(() => () => {}),
}))
```

Because each test mocks `src/api/admin` directly, the `api` axios instance stub is never called — it just prevents the import chain from crashing.

**Warning signs:** `Error: Cannot find module '#q-app/wrappers'` in any test.

### Pitfall 2: `flushPromises()` Omitted After Async Actions

**What goes wrong:** Test asserts DOM state before all `.then()` chains have resolved. `adminApi.getClients.mockResolvedValue(...)` is a microtask; the component's `onMounted` handler may not have finished.

**How to avoid:** After every action that triggers an API call: `await flushPromises()`.

### Pitfall 3: `$q.notify` Not Spied Correctly

**What goes wrong:** Tests assert `$q.notify` was called but the assertion is on an un-spied function, or the spy is set up before mount when `$q` doesn't exist yet.

**How to avoid:** Always set `wrapper.vm.$q.notify = vi.fn()` immediately after mount, before triggering the action.

### Pitfall 4: Per-Row Loading Map State Not Cleaned

**What goes wrong:** TopupsPage and ApiKeysDialog use `isApproving = ref({})` and `isRevoking = ref({})`. After a successful action the key is deleted. Tests that mount once and call actions multiple times can see stale loading state if mocks are not reset.

**How to avoid:** `vi.clearAllMocks()` in `beforeEach`. Mount a fresh component for each test using a factory function.

### Pitfall 5: v-if on ApiKeysDialog Not Wired

**What goes wrong:** In ClientsPage, `ApiKeysDialog` is guarded by `v-if="showApiKeysDialog && selectedClient"`. Testing for the presence of ApiKeysDialog before clicking "Manage Keys" will return empty.

**How to avoid:** Always click "Manage Keys" button first and await next tick before asserting the dialog renders.

### Pitfall 6: DlrDialog `watch({ immediate: true })`

**What goes wrong:** DlrDialog calls `loadDlr()` immediately when `sendRequestId` prop is non-null (via `watch` with `{ immediate: true }`). If `adminApi.getDlrForRequest` is not mocked before mount, the test throws an unhandled rejection.

**How to avoid:** Mock `adminApi.getDlrForRequest.mockResolvedValue(...)` **before** mounting DlrDialog with a non-null `sendRequestId`.

### Pitfall 7: AdminDashboardPage `Promise.all` — Partial Mock Failure

**What goes wrong:** AdminDashboardPage calls 6 APIs simultaneously in a `Promise.all`. If only some are mocked and others return `undefined`, the component throws because it spreads undefined data.

**How to avoid:** Mock all 6 endpoints before mounting: `getClients`, `getDeliveryStats`, `getCreditSummary`, `getCircuitBreakerHealth`, `getProviderStats`, `getWebhookHealth`. Even for error-path tests, stub the ones that succeed so only the target one rejects.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
